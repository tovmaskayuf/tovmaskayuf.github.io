# Essenta PRO — preview build

## What this repository is

This is a **built static export of a Next.js App Router site — generated output
only.** There is no source tree, no `package.json`, no build tooling, and no
content files. Nothing here can be regenerated by running a build; the only way
to change the site is to edit the generated artefacts in place.

Read that again before editing anything, because it drives every constraint
below.

Live at `https://tovmaskayuf.github.io/`, served by GitHub Pages from the
default branch. Every page ships `noindex, nofollow` and `robots.txt`
disallows all crawling, deliberately — the content is not approved and the
Armenian and Georgian translations are machine-drafted.

## Layout

```
uk/ en/ hy/ ka/ pl/    one locale each: index.html + index.txt (+ privacy, cookie-policy)
_next/static/chunks/   client JS bundles (minified)
_next/static/css/      one compiled Tailwind stylesheet
products/ brand/ retailers/ video/ fonts/    static assets
```

`uk` is the reference locale. The workflow so far has been: get Ukrainian
right first, then copy the structure to the other four and translate.

## The one thing that will bite you: two representations of every page

Each page exists **twice inside `index.html`**, and both must agree or React
throws a hydration mismatch (minified error #418) and re-renders client-side
with a visible flash:

1. **Server-rendered markup** — ordinary HTML in the document body.
2. **The RSC flight payload** — the React tree, split across
   `<script>self.__next_f.push([1,"…"])</script>` tags. This is the source of
   truth React hydrates from.

`index.txt` is the same flight payload as a standalone file (used for
client-side navigation). The concatenation of every `push()` in `index.html`
is **byte-identical** to `index.txt`. Keep it that way.

So a one-word copy change means editing: the markup, the flight pushes, and
`index.txt`. Hand-editing all three consistently is not realistic — use the
tooling approach described below.

### Flight payload shape

Newline-separated `key:json` rows. A row can reference another by the string
`"$L<key>"`, so a single visual section is often spread across several rows —
whether a node sits inline or behind a reference is a streaming detail, not
something meaningful. Rows are compact JSON (`separators=(",", ":")`).

Elements are `["$", tag, key, props]`. `"$L11"` in tag position is a **client
component** (next/image, Quiz, ProductMedia, RetailerLink, …): the flight
payload carries only its props, and its rendered HTML cannot be reconstructed
from them. Those subtrees have to be patched in the markup by matching on
something unique (an image `src`, a section `id`) rather than re-rendered.

## How to change this site safely

The approach that works — and what produced the current Ukrainian revision —
is a small Python harness that treats **the flight payload as the source of
truth** and *derives* the markup edit from it by re-rendering the affected
subtree with a faithful reimplementation of React's SSR output. That makes
the two representations incapable of drifting.

Essential details that took real debugging to get right:

- React writes `aria-hidden={true}` as `aria-hidden="true"`, **not** as the
  empty-attribute boolean shorthand. Boolean shorthand is only correct for
  genuine HTML boolean attributes (`autoplay`, `muted`, …).
- `<!-- -->` separators appear **only between two adjacent text children**.
  An empty-string child is dropped entirely, with no separator.
- SVG presentation props are hyphenated (`strokeWidth` → `stroke-width`).
- Attribute order follows prop insertion order.
- `next/image` emits `loading="lazy"` for normal images but omits it for
  `priority` ones, so attribute order differs between the two.

Verify after every change: re-render every server-side node in the tree and
assert its HTML appears verbatim in the markup. That catches drift before a
browser ever sees it.

### Tailwind classes

**Only classes already present in the compiled CSS work.** Tailwind cannot
generate new utilities without the build tooling, so `aspect-[16/9]` or
`max-w-[80rem]` silently do nothing if they were not used in the original
source. Check the stylesheet before using a class, or add a hand-written rule.

Hand-written rules live in a fenced block at the end of the stylesheet:

```
/*== essenta-ua-revision start ==*/ … /*== essenta-ua-revision end ==*/
```

Rewrite that block wholesale rather than editing rules scattered through the
compiled output. It is also where the small-screen fixes live.

### Client bundle patches

A few behaviours only exist in minified JS (`_next/static/chunks/app/[locale]/`)
— for example the quiz results heading and the cover-fit class on product
stills. Patches there are exact string replacements guarded by
`assert count == 1`, and `node --check` afterwards. Note these bundles are
**shared across all five locales**, so a fix there lands everywhere at once.

## Scroll-driven animations

The design leans heavily on `animation-timeline: view()` with offsets in
`rem` and ranges in `px`. Two bugs came out of this and both are fixed in the
custom CSS block — understand them before touching the animation rules:

- Entry keyframes translate up to `-32rem` (−512px) over ranges up to 980px.
  On a phone that is wider than the viewport and longer than it is tall, so
  blocks sat half off-screen and washed out *at the scroll position you would
  read them at*. Small screens now get a short vertical fade instead.
- `.slide-stack` children settled only after ~760px of travel, which left the
  "ready to order" panel looking like an empty white rectangle and pushed the
  document 360px wider than the viewport.

When judging these visually, **full-page screenshots lie** — the stitching
captures each strip at a different scroll offset, so animated blocks appear
half-finished or blank. Take viewport-sized screenshots after scrolling to a
section, or neutralise the animations first.

Note `body` has `overflow-x: clip`, so a `scrollWidth` larger than
`clientWidth` does *not* necessarily mean a horizontal scrollbar. Check
whether the page actually scrolls before chasing it.

## Verifying a change

Serve the directory and drive it with a real browser:

```
python3 -m http.server 8099
```

Worth checking every time:

- **Zero page errors.** React error #418 means the markup and flight payload
  disagree.
- **Horizontal overflow at 320/360/390/414/640px.** 320 is the tightest — the
  header logo, menu button and language select only just fit.
- **Broken images** (`naturalWidth === 0`). Allow generous time: gallery
  thumbnails are lazy and live inside closed `<details>` panels, so they
  report broken until scrolled to and expanded.
- The flight/markup consistency assertion described above.

The bundled Chromium has **no H.264 support**, so `.mp4` playback cannot be
verified locally — every video on the site fails there, including ones that
were fine before any change. Check the encode with `ffprobe` instead.
